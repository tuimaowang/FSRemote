## Context

当前 `DeviceGrid` 每秒收集所有远控窗口的统计快照，调用 `RemoteQualityCoordinator::evaluate()`，再把决策交给每个 `RemoteDesktopWindow`。旧实现同时承担模式解析、窗口角色分配、性能压力判断、FPS滞回、后台数量梯度和码率计算，导致一次焦点变化或统计噪声可能触发多层状态重置。

远控协议已经支持不断流修改分辨率、FPS、码率和优先级，因此本次不重写连接或协议。重构目标是缩小协调器职责：只把窗口快照映射为稳定角色，并在角色或静态档案发生变化时生成确定的质量请求。

## Goals / Non-Goals

**Goals:**

- 让单窗口、多窗口焦点、多窗口后台、最小化和软件回退各自拥有固定且可解释的质量档案。
- 删除接收FPS、解码耗时、丢包、Presenter丢帧和恢复滞回对质量请求的运行时改写。
- 保持现有 `RemoteQualityDecision`、在线质量协议和窗口生命周期接口兼容，降低重构范围。
- 让每次角色变化最多产生一次新的质量请求，静态运行期间不重复切档。
- 使用纯C++策略测试覆盖角色选择、焦点切换、窗口关闭、最小化和软件回退。

**Non-Goals:**

- 本次不删除 WebRTC 会话、D3D11 Presenter、纹理队列、输入或剪贴板代码。
- 本次不承诺在任何硬件上提供无限制的原始分辨率/60 FPS。
- 本次不引入新的线程、网络协议或持久化配置格式。

## Decisions

### 1. 用静态角色档案替代性能驱动降档

定义单窗口和多窗口质量档案，每个档案包含前台、后台和软件/最小化之外的静态参数。单窗口可见窗口使用单窗口前台档；存在多个已注册窗口时，唯一真实焦点窗口使用多窗口前台档，其余可见窗口使用多窗口后台档。

替代方案：继续保留压力采样和滞回，只调低阈值。拒绝，因为当前问题正是多种信号共同改写请求，降低阈值会增加切档而不是稳定输出。

### 2. 角色变化才触发质量请求

协调器每次评估仍可被现有定时器调用，但只要 `RemoteQualityDecision` 的角色和有效参数不变，就返回相同决策；窗口已有的 payload 去重继续作为第二道保护。性能统计只由诊断/覆盖层消费，不参与决策。

替代方案：删除定时评估并在每个窗口事件中手动触发。拒绝，因为焦点和窗口生命周期已经集中在 `DeviceGrid`，保留现有入口可以减少跨模块改造。

### 3. 保留安全档优先级

最小化或隐藏窗口继续使用全局最小化分辨率/FPS；软件回退继续使用固定的低分辨率/低FPS档。安全档优先于单窗口或多窗口前台档，退出安全状态后立即恢复对应静态角色档。

替代方案：让最小化窗口也走后台档。拒绝，因为最小化窗口的资源目标和可见后台不同，混用会导致恢复时请求不一致。

### 4. 删除协调器内部滞回状态

移除 `WindowState`、FPS索引、压力起止时间、恢复起止时间和后台数量梯度函数。保留性能采样结构和 `RemotePerformanceSignalSampler`，但只用于现有状态显示与诊断，避免无关调用方破坏接口。

## Risks / Trade-offs

- [Risk] 固定档不能自动适应极差网络。→ 保留 WebRTC 自身拥塞控制、Host 限制和软件回退；协调器只停止主动抖动。
- [Risk] 多窗口后台固定档在高端机器上可能浪费性能。→ 质量档集中在文件顶部，后续可直接调整，不需要重写策略。
- [Risk] 删除旧滞回后某些旧测试仍期待自动60/45/30。→ 同步重写策略测试，明确新的静态角色契约。

## Migration Plan

1. 先替换协调器实现和纯策略测试，不改协议和窗口生命周期。
2. 编译并运行 `fsremote_remote_quality_coordinator_tests`。
3. 关闭现有 `FSRemote.exe` 后执行一次 Release x64 链接，启动新程序做单窗口、双窗口焦点切换和最小化恢复验证。
4. 若新档位不合适，只修改质量档案常量；回滚时恢复 `RemoteQualityCoordinator.cpp/.h` 和对应测试即可。

## Open Questions

- 多窗口前台档默认使用 `P1080/60` 还是 `Native/60`，先采用前者以降低4K源的解码和呈现压力。
- 后台固定FPS默认值先采用10 FPS，是否进一步降到5 FPS由实机多窗口测试决定。
